### 0.1 为什么这件事必须现在做

02 和 03 解决的都是**一次性返回**的调用：发出去，等 5–10 秒，拿到一个完整对象，返回。

流式接口不是这样。它返回的东西**不是结果，是一个还在生产结果的管道**。这带来三个 02/03 完全没有覆盖的问题：

| 问题       | 一次性返回      | 流式返回                  |
| -------- | ---------- | --------------------- |
| 什么时候拿到结果 | 函数返回时就全有了  | 函数返回时一个字都没有，得一直 `for` |
| 能不能重复读   | 能，对象就在手里   | 不能，走过一遍就空了            |
| 要不要关掉    | 不用，没有可关的东西 | **必须关**，背后是一条 HTTP 连接 |

第三条最容易被忽略，也是本节花最大篇幅讲 `with` 的原因。

## 1. 前置知识：三个概念

### 1.1 `for` 到底在做什么（迭代协议）

`for x in obj` 不是语法魔法。它只做三件事：

1. 调 `iter(obj)`，拿到一个**迭代器**；
2. 反复调 `next(迭代器)`，每次拿到一个值；
3. 捕获 `StopIteration`，循环结束。

不信就自己写一个类，在里面打印，看 `for` 到底调了什么、调了几次：

```python
class Counter:
    def __init__(self, n):
        self.n = n
        self.i = 0

    def __iter__(self):
        print("  [__iter__ 被调用]")
        return self

    def __next__(self):
        if self.i >= self.n:
            raise StopIteration
        self.i += 1
        return self.i


for x in Counter(2):
    print("  拿到", x)
```

```text
  [__iter__ 被调用]
  拿到 1
  拿到 2
```

再手写一遍展开，确认它跟 `for` 是同一个东西：

```python
it = iter(Counter(2))
while True:
    try:
        print("  next ->", next(it))
    except StopIteration:
        print("  StopIteration，循环结束")
        break
```

```text
  [__iter__ 被调用]
  next -> 1
  next -> 2
  StopIteration，循环结束
```

**关键观察：`__iter__` 只被调用一次，之后全是 `__next__`。**

这条观察解释了后面的一切。迭代器身上那个「读到哪了」的位置是**有状态的**，而且只往一个方向走、不会自己回退。所以：

> 「只能遍历一次」不是生成器的怪癖，是迭代协议本身的性质。任何迭代器都这样。

（有个例外：`list` / `str` / `dict` 这些是**可迭代对象**，不是迭代器。你 `for` 一个列表一千次都行，因为每次 `iter(列表)` 都会造一个**新的**迭代器。区别就在于「位置」存在谁身上：存在容器里 → 可以反复遍历；存在迭代器自己身上 → 只能走一遍。）

### 1.2 生成器：函数体里有 `yield` 的函数

函数体里出现 `yield`，这个函数就变成**生成器函数**。它的行为和普通函数有三处根本区别，我一条条跑给你看。

```python
def counter(n):
    print("  [进入函数体]")
    for i in range(n):
        print(f"  [即将 yield {i}]")
        yield i
    return "我是 return 的值，不是 yield 的"


g = counter(3)
print("type(g) =", type(g).__name__)
```

```text
type(g) = generator
```

**注意：只打印了一行。** 那句 `[进入函数体]` 没有出现——说明**函数体一行都没跑**。

现在开始推进它。**这一段接上面同一段代码，`g` 就是上面那个 `counter(3)` 的返回值**，中间没有重新定义：

```python
print("next(g) =", next(g))
print("next(g) =", next(g))
print("next(g) =", next(g))
try:
    next(g)
except StopIteration as e:
    print("第四次 next 抛 StopIteration，e.value =", repr(e.value))
```



```text
  [进入函数体]
  [即将 yield 0]
next(g) = 0
  [即将 yield 1]
next(g) = 1
  [即将 yield 2]
next(g) = 2
  [循环结束，准备 return]
第四次 next 抛 StopIteration，e.value = '我是 return 的值，不是 yield 的'
```

三处区别，逐条对应上面两段输出：

|        | 普通函数        | 生成器函数                                       |
| ------ | ----------- | ------------------------------------------- |
| 调用时做什么 | 立刻执行函数体     | **只造一个对象就返回，函数体一行不跑**                       |
| 怎么拿到结果 | 直接用返回值      | 必须 `next()` 或 `for` 推进，一次拿一个                |
| 结束时    | 正常 `return` | 抛 `StopIteration`，`return` 的值藏在 `e.value` 里 |
| 能跑几次   | 每次调用从头来     | **一个对象只能从头走到尾一次**                           |

第三条最容易懵：`return` 在生成器里**不是**「返回结果」，而是「结束信号 + 附带一个值」。那个值不在 `yield` 序列里，只在 `StopIteration.value` 里。日常几乎用不到，知道有这么回事就行。

第四条，跑给你看：

```python
def gen():
    for i in range(3):
        yield i

g = gen()
print("第一次 list(g):", list(g))
print("第二次 list(g):", list(g))
```

```text
第一次 list(g): [0, 1, 2]
第二次 list(g): []
```

**不是报错，是空列表。** 因为位置已经走到头了，再 `next` 只有 `StopIteration`，`list()` 收到空序列。这个坑在生产里表现为「日志打印时内容好好的，实际发出去是空的」——因为你之前在别处 `for` 过一遍了。

想再来一遍，只能重新调用一次生成器函数造个新的。

### 1.3 `with` 的展开

```python
with 表达式 as 变量:
    代码块
```

等价于：

```python
管理器 = 表达式              # ① 先构造对象
变量 = 管理器.__enter__()    # ② 再进
try:
    代码块
finally:
    管理器.__exit__(...)     # ③ 无论如何都出
```

顺序里藏着一个反直觉的点。我写了个会打印每一步的类：

```python
class Probe:
    def __init__(self):
        print("  [__init__]")

    def __enter__(self):
        print("  [__enter__]")
        return self

    def __exit__(self, exc_type, exc_val, tb):
        print("  [__exit__] exc_type =", exc_type.__name__ if exc_type else None)
        return False


with Probe():
    print("  [body]")
```

```text
  [__init__]
  [__enter__]
  [body]
  [__exit__] exc_type = None
```

**`__init__` 在 `__enter__` 之前。** 所以「进入 with 块」其实是两步：先构造、再 `__enter__`。

这有个直接后果：**如果构造函数就抛异常，`__exit__` 根本不会被调用**（对象都没建成，没有可调用的方法）。所以「需要善后的初始化」不能放在 `__init__` 里，必须放 `__enter__`——本项目里 `TimedSpan` 的计时起点就是这么定的（§8.3 会讲）。

## 2. 知识衔接：03 的 `@retry` 在流式上完全失效

这一节是本篇最重要的一段，也是 04 非学不可的理由。

03 结束时你有了 `@retry`，包在普通函数上很好用。现在把它包在**生成器函数**上，会发生什么？我实测了：

```python
from w02.decorators import retry

calls = []


@retry(sleep=lambda s: None)
def stream_text() -> object:
    calls.append(1)

    def _gen():
        yield "第一段"
        raise TimeoutError("流到一半断了")

    return _gen()


g = stream_text()
print("① 返回:", type(g).__name__, "| 此时调用次数:", len(calls))
try:
    for piece in g:
        print("② 拿到:", piece)
except TimeoutError as e:
    print("③ 抛出:", type(e).__name__, e)
print("④ 最终调用次数:", len(calls))
```

```text
① 返回: generator | 此时调用次数: 1
② 拿到: 第一段
③ 抛出: TimeoutError 流到一半断了
④ 最终调用次数: 1
```

三件事同时发生了，每一件都不对劲：

1. **调用次数是 1**，一次都没重试。
2. **抛的是裸 `TimeoutError`**，不是 02 里定义的 `RetryableError`——说明连 `classify()` 都没走到。
3. 装饰器看起来「成功了」，因为它确实没报错。

### 2.1 为什么会这样

把 03 的 `wrapper` 拆开看：

```python
def wrapper(*args, **kwargs):
    return retry_call(lambda: func(*args, **kwargs), ...)
    #                      └─ 对生成器函数来说，这一步只是「造了个对象」
```

对普通函数，`func(*args)` 会**执行函数体**，出错就在这一行出错，`retry_call` 的 `try/except` 接得住。

对生成器函数，`func(*args)` **只是返回一个 `generator` 对象**，函数体一行没跑。所以 `retry_call` 看到的是「一次调用，顺利返回」——它认为成功了。

真正的异常发生在你 `for piece in g:` 去推进它的时候，而那时 `retry_call` 的 `try/except` 栈早就退出去了（函数已经 return 了，栈帧没了）。

**一句话概括：装饰器包住的是「函数的调用」，包不住「被推迟到未来的执行」。**

### 2.2 这个坑在生产里长什么样

你会写出这样的代码，并且以为它是安全的：

```python
@retry
def stream_answer(question: str):
    ...  # 返回生成器
```

然后线上偶发断流，你去看日志，发现重试记录一条都没有。你会先怀疑 `@retry` 写错了，再怀疑网络，最后才想到：**流式路径从头到尾没被保护过**。

### 2.3 正确的做法（本节不实现，留给 W3）

分两种情况：

| 情况                     | 能重试吗   | 怎么做                         |
| ---------------------- | ------ | --------------------------- |
| 建流那一步就失败（`create` 抛异常） | **能**  | 重试 `create` 这个调用本身，它是一次普通调用 |
| 流已经吐了字，中途断了            | **不能** | 已经显示给用户的字收不回来，重来会重复         |

所以流式的重试策略是：**保护「建立连接」，不保护「遍历过程」**。遍历中断了只能把已收到的部分交出去（这就是 `collect_partial` 的用途），然后由上层决定要不要从头再来一条新的流。

`@retry` 不加改造直接用在流式路径上，属于「看起来有保护，实际裸奔」。这是本节最该记住的一条。

## 3. 概念地图（补充）：本节的三个函数各管什么

正文马上要进代码了。先看这张表，它回答「我要写三个函数，为什么不是一个」：

| 函数                 | 输入          | 输出              | 职责                 |
| ------------------ | ----------- | --------------- | ------------------ |
| `open_text_stream` | client、提问文本 | 一条流（在 `with` 里） | **只负责打开和关闭**，不碰内容  |
| `iter_text`        | 一条流         | 一段段纯文本          | **只负责切分**，不碰连接     |
| `collect_partial`  | 一条流         | 整段文本 + 可能的异常    | **只负责汇聚与兜底**，不碰前两者 |

分开的理由是**它们的变化频率不同**：换供应商只改第一个；API 返回格式变了只改第二个；要不要保留半截内容只改第三个。合在一起，改任何一处都得动全部。

## 4. v1：直接 `for` 循环（能跑，一碰真实数据就崩）

最朴素的写法，跟 03 之前的 `retry_call(lambda: ...)` 是同一代东西。下面是这个函数的正文（单独看它跑不起来，因为它需要 `client`；完整可跑的脚本在紧接着的下一段）：

```python
def collect_v1(text, client):
    stream = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": text}],
        stream=True,

    parts = []
    for chunk in stream:
        parts.append(chunk.choices[0].delta.content)
```

看起来没问题。我用 `w02/fakes.py` 里的假流喂了三种真实形状的数据。完整脚本（可直接跑，`PYTHONPATH` 指到项目根）：

### 4.1 为什么真实流里会有这两种「怪块」

这不是我编的，是流式协议的正常形态。把一条真实的流摊开看：

| 第几块 | `choices` | `delta.content` | 是什么 |
|---|---|---|---|
| 1 | 1 个元素 | `"大模型"` | 正常内容 |
| 2 | 1 个元素 | `"应用"` | 正常内容 |
| 3 | 1 个元素 | `"开发"` | 正常内容 |
| 4 | 1 个元素 | `None` | 结束块，只带 `finish_reason="stop"` |
| 5 | **空列表** | —— | 真正的末块，`choices` 是 `[]` |

第 5 块我实测确认过：`len(last.choices)` 就是 `0`，取 `last.choices[0]` 抛 `IndexError: list index out of range`。

第 4 块也一样实测过：`c.choices[0].delta.content` 是 `None`（不是 `""`），`c.choices[0].finish_reason` 是 `'stop'`。

所以 v1 的两个「低级错误」其实一点都不低级——**你得先知道协议长什么样，才能写出正确的跳过条件**。

### 4.2 v1 的四个代价

| 代价 | 具体表现 | 实测证据 |
|---|---|---|
| **取字段不安全** | 空 `choices`、`None` 内容，两种崩溃都在正常路径上 | 上表 ①② |
| **连接不关** | 没有 `with`、没有 `close()`，全靠 GC 碰运气 | 三次都是 `closed = False` |
| **半截内容丢失** | 流断了，已经收到的字跟着异常一起消失 | ③ 抛 `TimeoutError`，`parts` 里的 `"第一段"` 一起没了 |
| **逻辑粘在业务里** | 每个调用点都要重抄一遍「循环 + 取 delta + 拼」 | —— |

第一条要纠正一个常见误解：**这不是「边界情况」，是每次都会走到的正常路径。** 只要一次调用正常结束，第 4、5 块一定会出现。

第二条的严重性取决于调用量。单次流式请求泄漏一条连接，看起来没事；一天一万次、连接池上限 100，就是「跑几小时后突然全部超时」。而且这类问题**不会报错**，只是越来越慢，非常难查。

第三条是产品层面的：用户已经看到「今天天气」四个字，然后界面变空白加一个报错框。他要的不是「一个错误」，是「至少把已经说了的那四个字留下」。

### 4.3 顺带确认一件事：`Stream` 真的有关闭能力

我查了本机 SDK 的 `Stream` 类：

```python
from openai import Stream

print("__enter__ :", hasattr(Stream, "__enter__"))
print("__exit__  :", hasattr(Stream, "__exit__"))
print("__iter__  :", hasattr(Stream, "__iter__"))
```

```text
close     : True
__enter__ : True
__exit__  : True
__iter__  : True
```

它在 openai 3.37.0 里已经自带上下文管理器协议，所以理论上可以写：

```python
with client.chat.completions.create(..., stream=True) as stream:
    ...
```

**但本项目不这么写。** 两个理由：

1. 老版本 SDK（以及不少其他厂商的客户端）没有实现 `__enter__`/`__exit__`，换一版就崩；
2. 我们要在「打开」这一步加东西（超时、重试、埋点），必须自己掌控 `create` 前后的代码。

自己包一层 `@contextmanager`，这两点都解决。

## 5. 生成器的四条铁律（都是实测的）

在写 v2 之前，把生成器的行为定死。四条，每条都有实测。

### 5.1 铁律一：调用不执行

已经在 §1.2 证明了。再补一个对偶的事实：**`iter_text(stream)` 调用之后，`stream` 一格都没被消费。**

测试里就是这么断言的：

```python
gen = iter_text(stream)
assert stream.iterated == 0    # 还没动
next(gen)
assert stream.iterated == 1    # 推进一步才动一格
```

这条的意义：**生成器让你可以「先传出去，要用时再算」。** 处理一条 10 万行的日志流，你不需要先把它读进内存——`for line in gen` 的时候才算一行。流式输出能边收边显示，也是同一个道理。

### 5.2 铁律二：只能走一遍

§1.2 的 `list(g)` 两次已经证明。这里补充它带来的**设计约束**：

```python
def build():
    return iter_text(stream)   # 返回生成器
```

如果你把这个返回值存成模块级常量、或者缓存起来给两个地方用，第二个用的地方会拿到空序列。正确做法是**每次用的时候重新调用生成器函数**。

测试里有一条专门守着它：

```python
def test_生成器遍历一次就空() -> None:
    gen = iter_text(FakeStream(full_pieces()))
    assert "".join(gen) == "大模型应用开发"
    assert list(gen) == []
```

### 5.3 铁律三：`yield` 是暂停，不是 `return`

这个区别决定了 `@contextmanager` 能工作。实测 `send()` 和 `yield from`：

```python
def echo():
    received = []
    while True:
        got = yield          # yield 也是表达式，能接住 send 进来的值
        if got is None:
            return received
        received.append(got)


g = echo()
next(g)                      # 必须先启动，推进到第一个 yield
print("send('a') ->", g.send("a"))
print("send('b') ->", g.send("b"))
try:
    g.send(None)
except StopIteration as e:
    print("结束时收到的列表:", e.value)
```

```text
send('a') -> None
send('b') -> None
结束时收到的列表: ['a', 'b']
```

三件事：

- `yield` **可以当表达式用**，`got = yield` 表示「暂停在这里，等外面塞个值进来赋给 `got`」。
- `send(v)` 的值会取代 `yield` 表达式的求值结果，同时生成器推进到下一个暂停点。
- **第一次必须用 `next()` 或 `send(None)` 启动**，直接 `send("a")` 会报 `TypeError: can't send non-None value to a just-started generator`。因为生成器还没跑到 `yield`，没地方接值。

`send()` 日常写业务代码几乎不用，但 `@contextmanager` 内部就是靠它把异常塞进 `yield` 那一行的（§7 会看到效果）。

`yield from` 是「把另一个可迭代对象整个转出去」的简写：

```python
def inner():
    yield 1
    yield 2


def outer():
    yield 0
    yield from inner()
    yield 3


print("yield from ->", list(outer()))
```

```text
yield from -> [0, 1, 2, 3]
```

它等价于 `for x in inner(): yield x`，但更短，而且会正确转发 `send()` 和 `return` 值。日常在「把多个生成器串起来」时用，比如把几个分页的结果拼成一条流。

### 5.4 铁律四：提前丢弃时，`finally` 靠不住

这条直接决定「能不能只靠生成器自己关连接」。实测：

```python
def gen_with_finally():
    try:
        for i in range(5):
            yield i
    finally:
        print("  [生成器的 finally 执行了]")


g = gen_with_finally()
for x in g:
    if x == 1:
        break
del g
```

```text
  [生成器的 finally 执行了]
```

看起来很好——`break` 之后 `del` 就触发了 `finally`。**但这是 CPython 的引用计数机制在帮忙，不是语言保证。** PyPy、或者有循环引用时（比如生成器被塞进一个引用自己的容器），`finally` 可能等到垃圾回收才跑，甚至永远不跑。

所以结论是：

> **不能靠「生成器被回收」来保证善后。** 想保证，就用 `with`，让 `finally` 在一个你明确控制的位置执行。

本节的做法正是这样：连接由 `open_text_stream` 的 `with` 负责，`iter_text` 只管切分，不管关。

## 6. `with` 协议：`__exit__` 到底收到什么

§1.3 讲了顺序，这里讲**参数**。`__exit__` 签名固定三个参数：

```python
def __exit__(self, exc_type, exc_val, tb):
    ...
```

它们在不同情况下是什么？实测三种：

```python
class Probe:
    def __init__(self, swallow=False):
        self.swallow = swallow

    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_val, tb):
        print("  exc_type =", exc_type.__name__ if exc_type else None)
        print("  exc_val  =", repr(exc_val))
        print("  tb       =", type(tb).__name__ if tb else None)
        return self.swallow


print("① 正常结束")
with Probe():
    print("  [body]")

print("② 体内抛异常，__exit__ 返回 False → 异常继续往上抛")
try:
    with Probe():
        raise ValueError("体内炸了")
except ValueError as e:
    print("  外层抓到:", type(e).__name__, e)

print("③ __exit__ 返回 True → 异常被吞掉")
with Probe(swallow=True):
    raise ValueError("本该炸")
print("  走到这里说明异常被吞了")
```

```text
① 正常结束
  [body]
  exc_type = None
  exc_val  = None
  tb       = None
② 体内抛异常，__exit__ 返回 False → 异常继续往上抛
  exc_type = ValueError
  exc_val  = ValueError('体内炸了')
  tb       = traceback
  外层抓到: ValueError 体内炸了
③ __exit__ 返回 True → 异常被吞掉
  exc_type = ValueError
  exc_val  = ValueError('本该炸')
  tb       = traceback
  走到这里说明异常被吞了
```

这张表要回答的问题是：**`with` 里面出错了，我能不能在 `__exit__` 里知道、能不能拦住。**

| `__exit__` 的返回值 | 效果 |
|---|---|
| `None` 或 `False` | 异常继续往上抛（**默认行为，绝大多数情况要这个**） |
| `True` | 异常被吞掉，`with` 后面的代码照常执行 |

第三条要特别警惕：**返回 `True` 等于把一个错误悄悄吃掉。** 除了「确实想让这个错误静默」的极少数场景（比如 `contextlib.suppress`），一律 `return False`。

本节的 `TimedSpan.__exit__` 就返回 `False`，测试里有一条专门守着：

```python
def test_块内异常不被吞() -> None:
    with pytest.raises(ValueError, match="块里炸了"):
        with timed_span("会炸", timer=Ticker(0.0, 0.0), sink=lambda n, s: None):
            raise ValueError("块里炸了")
```

另外两个细节，实测确认过：

**一、`__exit__` 在异常时也一定被调用**，包括 `break`、`return`、`continue` 跳出 `with` 块的情况。这就是「一定收尾」的来源。

**二、`__exit__` 自己抛异常会顶掉原来的异常。** 所以 `__exit__` 里不要写可能失败的操作（比如 `close()` 之后再打日志失败），否则你看到的是 `__exit__` 的错误，原始异常没了。真要打日志，包一层 `try/except`。

### 6.1 什么该做成上下文管理器

不是所有东西都值得。判断标准只有一条：**有没有「必须配对、且可能因为异常而漏掉」的两个动作。**

| 场景 | 配对的开始/结束 | 该做成吗 |
|---|---|---|
| 打开流 | `create()` / `close()` | ✅ 本节第一个产物 |
| 计时 | 记开始 / 记结束 | ✅ 本节第二个产物 |
| 打开文件 | `open()` / `close()` | ✅ 标准库已有 |
| 加锁 | `acquire()` / `release()` | ✅ 标准库已有 |
| 打个日志 | 开始打 / 结束打 | ❌ 没有需要成对释放的资源 |
| 建一个 dict | 建立 / 丢弃 | ❌ GC 会处理，不需要显式收尾 |

## 7. `@contextmanager`：用生成器写上下文管理器

自己写 `__enter__`/`__exit__` 两个方法，代码里有三处重复（一个类、两个方法名、两次状态赋值）。`contextlib.contextmanager` 让你用生成器写，规则只有一句：

> **`yield` 之前的代码 = `__enter__`；`yield` 之后的代码 = `__exit__`。**

### 7.1 先看不带 `try/finally` 会怎样

这是本节最容易踩的坑，我专门造了个反例：

```python
from contextlib import contextmanager


@contextmanager
def bad():
    print("  [enter]")
    yield 1
    print("  [exit —— 正常路径才会执行到这]")


try:
    with bad():
        raise ValueError("炸")
except ValueError:
    print("  外层抓到")
```

```text
  [enter]
  外层抓到
```

**`[exit]` 那行没有打印。**

原因是：`with` 体内抛的异常，会被 `@contextmanager` **注入到 `yield` 那一行**——等于在 `yield` 的位置 `raise` 了一次，于是生成器直接往外抛，`yield` 后面的语句根本没机会执行。

### 7.2 加上 `try/finally` 才对

```python
from contextlib import contextmanager


@contextmanager
def probe():
    print("  [yield 之前 = __enter__]")
    try:
        yield "我作为 as 的值"
    except ValueError as e:
        print("  [异常被注入到 yield 那一行] ->", type(e).__name__, e)
        raise
    finally:
        print("  [finally = 必然执行的 __exit__ 部分]")


print("① 正常路径")
with probe() as v:
    print("  [body] as v =", repr(v))

print("② 体内抛异常")
try:
    with probe():
        raise ValueError("炸")
except ValueError:
    print("  外层还是抓到了")
```

```text
① 正常路径
  [yield 之前 = __enter__]
  [body] as v = '我作为 as 的值'
  [finally = 必然执行的 __exit__ 部分]
② 体内抛异常
  [yield 之前 = __enter__]
  [异常被注入到 yield 那一行] -> ValueError 炸
  [finally = 必然执行的 __exit__ 部分]
  外层还是抓到了
```

三件事同时成立：

1. `yield` 的值就是 `as` 后面拿到的（`'我作为 as 的值'`）。
2. 体内抛的异常，你能在 `except` 里接住——它被塞进了 `yield` 那一行。
3. `finally` 在两条路径上都执行。

所以写 `@contextmanager` 的铁律是：

```python
@contextmanager
def 我的资源():
    资源 = 打开()
    try:
        yield 资源          # ← yield 必须在 try 里面
    finally:
        资源.close()        # ← 收尾必须放 finally
```

**`yield` 必须放在 `try` 里。** 少一个 `try`，你的 `close()` 就只在顺利时执行——而「顺利」恰恰是最不需要保证的情况。

### 7.3 还有一个反直觉点：函数体在 `with` 时才执行

`@contextmanager` 装饰出来的东西，调用时**什么都不做**，只返回一个对象；函数体要等 `with` 才跑。

演示第 ⑤ 段实测：

```text
⑤ 不进入 with 就不发请求
   拿到上下文管理器后 create_calls = 0
   进入 with 后 create_calls = 1
```

这跟 §1.2「生成器调用不执行」是同一件事——因为 `@contextmanager` 本身就是把生成器函数包了一层。测试里有一条守着：

```python
def test_不进入with不发请求() -> None:
    client = FakeClient(full_pieces())
    cm = open_text_stream(client, "原文")
    assert client.create_calls == 0
    with cm as stream:
        assert client.create_calls == 1
        collect(stream)
```

**实践含义：**「打开连接」这件事被推迟到了 `with`，这正好是我们想要的——你可以在 `with` 之前做完所有参数校验，不会白开一条连接。

### 8.1 `w02/fakes.py`

````python
"""W2-04 · 测试与演示共用的假流对象。

真实 SDK 的 Stream 背后是一条活着的 HTTP 连接，测试里造不出来（也不该造）。
这里用最小实现顶替它：可迭代 + 有 close() + 记录自己有没有被关。

一个刻意的设计：pieces 列表里可以混入异常实例，表示「遍历到这一格就炸」。
于是「发三段然后断流」只需要写 [chunk("第一段"), TimeoutError("断了")]。

这个模块不产生任何输出，也没有演示入口。
"""
from __future__ import annotations

from collections.abc import Iterable, Iterator
from types import SimpleNamespace
from typing import Any

from openai.types.chat import ChatCompletionChunk

MODEL = "gpt-4o-mini"


def make_chunk(content: str | None, finish_reason: str | None = None) -> ChatCompletionChunk:
    """造一个流式碎片。content=None 用于模拟结束块。"""
    return ChatCompletionChunk.model_validate({
        "id": "chatcmpl-fake",
        "object": "chat.completion.chunk",
        "created": 0,
        "model": MODEL,
        "choices": [{
            "index": 0,
            "finish_reason": finish_reason,
            "delta": {"role": None, "content": content},
        }],
    })


def empty_chunk() -> ChatCompletionChunk:
    """流真正结束时发的那一块：choices 是空列表。"""
    return ChatCompletionChunk.model_validate({
        "id": "chatcmpl-fake",
        "object": "chat.completion.chunk",
        "created": 0,
        "model": MODEL,
        "choices": [],
    })


class FakeStream:
    """顶替 SDK 的 Stream：能 for、能 close、能被检查。"""

    def __init__(self, pieces: Iterable[Any]) -> None:
        self._pieces = list(pieces)
        self.closed = False
        self.iterated = 0

    def __iter__(self) -> Iterator[Any]:
        for piece in self._pieces:
            if isinstance(piece, BaseException):
                raise piece
            self.iterated += 1
            yield piece

    def close(self) -> None:
        self.closed = True


class FakeClient:
    """顶替 openai.OpenAI：只需要 client.chat.completions.create 这一条链。"""

    def __init__(self, pieces: Iterable[Any]) -> None:
        self.pieces = list(pieces)
        self.last_stream: FakeStream | None = None
        self.create_calls = 0
        self.last_kwargs: dict[str, Any] = {}
        self.chat = SimpleNamespace(completions=SimpleNamespace(create=self._create))

    def _create(self, **kwargs: Any) -> FakeStream:
        self.create_calls += 1
        self.last_kwargs = kwargs
        if kwargs.get("stream") is not True:
            raise AssertionError("这个假 client 只服务流式路径")
        self.last_stream = FakeStream(self.pieces)
        return self.last_stream
````


三处需要解释：

**① `make_chunk` 用 `model_validate` 造对象。** 这直接复用了 01 学的 `model_validate`——`ChatCompletionChunk` 是一个 Pydantic 模型，给它一个形状正确的字典，它就能造出「看起来像真的」的 chunk。不需要 API key，不需要联网。

**② `pieces` 里混入异常实例。** `FakeStream.__iter__` 里有一行 `if isinstance(piece, BaseException): raise piece`。于是「发三段然后断流」写成一个列表就够了：

```python
pieces = [make_chunk("第一段"), make_chunk("第二段"), TimeoutError("流断了")]
```

这是测试手法，不是生产代码。它的价值在于：**断流这件事变得可编程、可复现。** 02 里造 SDK 异常、03 里注入 `ticks`，都是同一个思路。

**③ `FakeClient` 用 `SimpleNamespace` 拼出 `client.chat.completions.create` 这条链。** 真 SDK 的这条链有四层属性，用两个 `SimpleNamespace` 就够模拟，不需要 mock 库。

### 8.2 `w02/streaming.py`

````python
"""W2-04 · 生成器 + 上下文管理器：把流式响应切成文本，并保证连接一定关掉。

一句话：`yield` 让函数边算边给，`with` 让收尾一定发生。

为什么需要这一层：
  1. 流式接口返回的是迭代器，不是一个完整对象 —— 只能往前走一遍；
  2. 迭代器背后挂着一条 HTTP 连接，没关就是资源泄漏；
  3. 碎片流里有 choices 为空的块和 content 为 None 的块，直接取字段会崩。

运行演示：..\\.venv\\Scripts\\python.exe -m w02.streaming
"""
from __future__ import annotations

from collections.abc import Iterable, Iterator
from contextlib import contextmanager
from typing import Any

DEFAULT_MODEL = "gpt-4o-mini"


@contextmanager
def open_text_stream(
    client: Any,
    text: str,
    *,
    model: str = DEFAULT_MODEL,
) -> Iterator[Iterable[Any]]:
    """打开一条流，离开 with 块时一定 close()。

    注意「打开」这件事发生在 __enter__ 里（也就是第一次 with 时），
    不是在调用 open_text_stream() 的那一刻 —— @contextmanager 的函数体
    要等 with 才跑。所以单纯拿到这个对象不会发出任何请求。
    """
    stream = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": text}],
        stream=True,
    )
    try:
        yield stream
    finally:
        stream.close()


def iter_text(stream: Iterable[Any]) -> Iterator[str]:
    """把 chunk 流切成纯文本片段。

    两次跳过分别对应两种真实崩溃：
      - choices 为空 → 直接取 [0] 会 IndexError
      - content 为 None → 拼进字符串会 TypeError
    """
    for chunk in stream:
        if not chunk.choices:
            continue
        piece = chunk.choices[0].delta.content
        if piece:
            yield piece


def collect(stream: Iterable[Any]) -> str:
    """拼成整段文本。中途断流就抛，已经收到的碎片随异常一起丢掉。"""
    return "".join(iter_text(stream))


def collect_partial(stream: Iterable[Any]) -> tuple[str, Exception | None]:
    """拼成整段文本；中途断流则返回「已收到的部分」和那个异常。

    返回值是二元组而不是抛异常，因为调用方往往两样都要：
    既要告诉用户「下面没了」，又要保住上面已经显示出来的字。
    """
    parts: list[str] = []
    try:
        for piece in iter_text(stream):
            parts.append(piece)
    except Exception as exc:
        return "".join(parts), exc
    return "".join(parts), None


def _demo() -> None:
    from w02.fakes import FakeClient, empty_chunk, make_chunk

    def full_pieces() -> list[Any]:
        return [
            make_chunk("大模型"),
            make_chunk("应用"),
            make_chunk("开发"),
            make_chunk(None, finish_reason="stop"),
            empty_chunk(),
        ]

    print("① 完整地收集一条流")
    client = FakeClient(full_pieces())
    with open_text_stream(client, "原文") as stream:
        print("   结果:", repr(collect(stream)))
    print("   stream.closed =", client.last_stream.closed)

    print("② 边收边打印（真正的流式体验）")
    client = FakeClient(full_pieces())
    with open_text_stream(client, "原文") as stream:
        for piece in iter_text(stream):
            print("    收到:", piece)

    print("③ 提前 break：连接照样关闭")
    client = FakeClient(full_pieces())
    with open_text_stream(client, "原文") as stream:
        for piece in iter_text(stream):
            print("    只取第一段:", piece)
            break
    print("   stream.closed =", client.last_stream.closed)

    print("④ 流到一半断掉：已收到的内容还在")
    client = FakeClient([make_chunk("第一段"), TimeoutError("流断了")])
    with open_text_stream(client, "原文") as stream:
        text, error = collect_partial(stream)
    print("   已收到:", repr(text), "| 异常:", type(error).__name__)
    print("   stream.closed =", client.last_stream.closed)

    print("⑤ 不进入 with 就不发请求")
    client = FakeClient(full_pieces())
    cm = open_text_stream(client, "原文")
    print("   拿到上下文管理器后 create_calls =", client.create_calls)
    with cm as stream:
        print("   进入 with 后 create_calls =", client.create_calls)


if __name__ == "__main__":
    _demo()
````

三个函数，逐个说清「为什么这么写」。

**`open_text_stream`：`try/finally` 包住 `yield`，`close()` 放 `finally`。**

```python
stream = client.chat.completions.create(...)
try:
    yield stream
finally:
    stream.close()
```

`create` 放在 `try` **外面**，是有意的：如果 `create` 自己抛异常，根本没有 `stream` 对象，也就没有东西要关。把它放 `try` 里面反而会让 `finally` 去访问一个没赋值的变量，报 `UnboundLocalError`。

**`iter_text`：两个 `if` 对应两种崩溃。**

```python
if not chunk.choices:      # 空列表 → 跳过（否则 IndexError）
    continue
piece = chunk.choices[0].delta.content
if piece:                  # None 或 "" → 跳过（否则 TypeError 或被拼进空串）
    yield piece
```

注意 `if piece` 而不是 `if piece is not None`：这样 `""` 也会被跳过。效果一样（`""` 拼进去不影响结果），但能少一次 `yield`。副作用是 `" "`（空格）**会**被保留——这是对的，空格是内容的一部分。测试里两条分别守着这两种情况。

**`collect` 和 `collect_partial`：一个抛、一个兜。**

```python
def collect(stream):
    return "".join(iter_text(stream))          # 断流就抛

def collect_partial(stream):
    parts = []
    try:
        for piece in iter_text(stream):
            parts.append(piece)
    except Exception as exc:
        return "".join(parts), exc              # 断流给半截
    return "".join(parts), None
```

为什么返回二元组而不是自定义异常？因为调用方要的是**两样东西**：已经收到的文字（要显示给用户）、以及出了什么错（要记日志/上报）。用异常表达的话，「半截内容」就得挂在异常的属性上，读起来别扭，还容易被 `except` 顺手吞掉。

`except Exception` 而不是 `BaseException`：`KeyboardInterrupt`（Ctrl+C）不该被吞，用户按了就该停。

### 8.3 `w02/spans.py`

````python
"""W2-04 · 上下文管理器：把「一定收尾」做成可复用的协议。

和 03 的 @timed 对照着看：
  装饰器     包住「一次函数调用」，跨函数复用；
  上下文管理器 包住「一段代码块」，跨语句复用 —— 一段 with 里可以有十行。

计时逻辑是同一套，区别只在包的是什么。

运行演示：..\\.venv\\Scripts\\python.exe -m w02.spans
"""
from __future__ import annotations

import logging
import time
from collections.abc import Callable, Iterator
from contextlib import contextmanager
from types import TracebackType

logger = logging.getLogger(__name__)

Timer = Callable[[], float]
Sink = Callable[[str, float], None]


class TimedSpan:
    """用类实现的上下文管理器：__enter__ 开始计时，__exit__ 结束时记录。

    计时起点放在 __enter__ 而不是 __init__，是因为 with 的展开顺序是
    「先构造、再 enter」：构造函数跑完到真正进入代码块之间可能隔了一段
    （比如你还写了别的语句），那段时间不该算进来。
    """

    def __init__(
        self,
        name: str,
        *,
        timer: Timer = time.perf_counter,
        sink: Sink | None = None,
    ) -> None:
        self.name = name
        self.elapsed: float | None = None
        self.exc_type: type[BaseException] | None = None
        self._timer = timer
        self._sink = sink
        self._started: float | None = None

    def __enter__(self) -> TimedSpan:
        self._started = self._timer()
        return self

    def __exit__(
        self,
        exc_type: type[BaseException] | None,
        exc: BaseException | None,
        tb: TracebackType | None,
    ) -> bool:
        if self._started is None:
            raise RuntimeError("TimedSpan 必须作为上下文管理器使用")
        self.elapsed = self._timer() - self._started
        self.exc_type = exc_type

        if self._sink is not None:
            self._sink(self.name, self.elapsed)
        else:
            logger.info(
                "%s 耗时 %.3fs%s",
                self.name,
                self.elapsed,
                "（块内出错）" if exc_type is not None else "",
            )

        return False


@contextmanager
def timed_span(
    name: str,
    *,
    timer: Timer = time.perf_counter,
    sink: Sink | None = None,
) -> Iterator[TimedSpan]:
    """同一件事的生成器写法。yield 之前是 __enter__，之后是 __exit__。

    这里把整个工作委托给 TimedSpan，不重复实现，是为了让两种写法的
    行为严格一致 —— 否则你会在「异常时到底记不记录」这种细节上踩两次坑。
    """
    with TimedSpan(name, timer=timer, sink=sink) as span:
        yield span


def _demo() -> None:
    records: list[tuple[str, float]] = []

    def sink(name: str, elapsed: float) -> None:
        records.append((name, elapsed))

    print("① 类写法")
    ticks = iter([0.0, 3.0])
    with TimedSpan("调模型", timer=lambda: next(ticks), sink=sink) as span:
        print("   （假装这里调了一次模型）")
    print("   span.elapsed =", span.elapsed)

    print("② 生成器写法（同一个东西）")
    ticks = iter([10.0, 10.5])
    with timed_span("解析 JSON", timer=lambda: next(ticks), sink=sink) as span:
        print("   （假装这里解析了一次）")
    print("   span.elapsed =", span.elapsed)

    print("③ 块里抛异常：照样记录，异常不被吞")
    ticks = iter([0.0, 0.0])
    try:
        with timed_span("会炸的块", timer=lambda: next(ticks), sink=sink) as span:
            raise ValueError("块里炸了")
    except ValueError as exc:
        print("   外层抓到:", type(exc).__name__, exc)
    print("   span.exc_type =", span.exc_type.__name__)
    print("   span.elapsed  =", span.elapsed)

    print("④ 记录汇总（含正常与异常两类）")
    for name, elapsed in records:
        print(f"   {name:<10} {elapsed}")


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    _demo()
````

四件事值得单独说。

**① 计时起点在 `__enter__`，不在 `__init__`。**

```python
def __enter__(self) -> TimedSpan:
    self._started = self._timer()
    return self
```

这正是 §1.3 那个实测的用处：`with` 是「先构造、再 enter」。如果你在 `__init__` 里开始计时，那么从构造到真正进块之间的时间（可能你中间写了别的语句）也会被算进去。测试里有一条钉着：

```python
def test_构造时不调用timer() -> None:
    ticker = Ticker(0.0, 1.0)
    span = TimedSpan("x", timer=ticker, sink=lambda n, s: None)
    assert ticker.calls == 0      # 构造时一次都没调
    with span:
        pass
    assert ticker.calls == 2      # enter 一次、exit 一次
```

**② `__exit__` 返回 `False`，异常照常上抛。**

```python
return False
```

理由见 §6：返回 `True` 会把错误吃掉，而「块里出错」是需要让上层知道的。

**③ `timed_span` 不重写逻辑，直接委托给 `TimedSpan`。**

```python
@contextmanager
def timed_span(name, *, timer=..., sink=...) -> Iterator[TimedSpan]:
    with TimedSpan(name, timer=timer, sink=sink) as span:
        yield span
```

这个写法看着有点绕（上下文管理器里再套一个上下文管理器），但它是**唯一能保证两种写法行为严格一致**的方式。如果我把计时逻辑抄一遍到 `timed_span` 里，早晚会在「异常时到底记不记录」这种细节上出现分歧。测试里两条用例分别验两种写法，数值必须一样。

**④ `span` 对象可以被复用。** `__enter__` 每次重置 `_started`，所以同一个 `TimedSpan` 实例可以进出多次，每次都独立计时。测试 `test_每次进入各自计时` 用四个时间戳验了这一点（第一次 `2.0`、第二次 `0.25`）。

````python
16 条，四组：切分 5、惰性 2、上下文 5、半截内容 4。

全部不联网、不真等、不花钱：FakeClient 顶替 SDK 的客户端，
````

| 组 | 条数 | 守什么 |
|---|---|---|

| 惰性 | 2 | 调用不消费、遍历一次就空 |

### 9.3 `w02/test_spans.py`（9 条）

````python
"""W2-04 · spans 的测试。

9 条，三组：计时 4、异常路径 3、日志兜底 2。

关键手法跟 03 一样：把 timer 注入成一个「按剧本报数」的函数，
于是耗时断言可以写等号，而不是「大约」。
"""
from __future__ import annotations

import logging

import pytest

from w02.spans import TimedSpan, timed_span


class Ticker:
    """按剧本依次返回时间戳，用完之后报错（防止多调一次被悄悄放过）。"""

    def __init__(self, *values: float) -> None:
        self._values = list(values)
        self.calls = 0

    def __call__(self) -> float:
        self.calls += 1
        if not self._values:
            raise AssertionError("timer 被调用的次数超出剧本")
        return self._values.pop(0)


def test_类写法记录耗时() -> None:
    records: list[tuple[str, float]] = []
    ticker = Ticker(0.0, 3.0)
    with TimedSpan("调模型", timer=ticker, sink=lambda n, s: records.append((n, s))) as span:
        pass
    assert span.elapsed == 3.0
    assert records == [("调模型", 3.0)]


def test_生成器写法记录耗时() -> None:
    records: list[tuple[str, float]] = []
    ticker = Ticker(10.0, 10.5)
    with timed_span("解析", timer=ticker, sink=lambda n, s: records.append((n, s))) as span:
        pass
    assert span.elapsed == 0.5
    assert records == [("解析", 0.5)]


def test_构造时不调用timer() -> None:
    ticker = Ticker(0.0, 1.0)
    span = TimedSpan("x", timer=ticker, sink=lambda n, s: None)
    assert ticker.calls == 0
    assert span.elapsed is None
    with span:
        pass
    assert ticker.calls == 2


def test_每次进入各自计时() -> None:
    records: list[tuple[str, float]] = []
    span = TimedSpan("复用", timer=Ticker(0.0, 2.0, 100.0, 100.25),
                     sink=lambda n, s: records.append((n, s)))
    with span:
        pass
    first = span.elapsed
    with span:
        pass
    assert first == 2.0
    assert span.elapsed == 0.25
    assert len(records) == 2


def test_正常结束时exc_type为None() -> None:
    with timed_span("正常", timer=Ticker(0.0, 1.0), sink=lambda n, s: None) as span:
        pass
    assert span.exc_type is None


def test_块内异常也记录耗时() -> None:
    records: list[tuple[str, float]] = []
    with pytest.raises(ValueError):
        with timed_span("会炸", timer=Ticker(0.0, 0.75),
                        sink=lambda n, s: records.append((n, s))) as span:
            raise ValueError("块里炸了")
    assert span.elapsed == 0.75
    assert span.exc_type is ValueError
    assert records == [("会炸", 0.75)]


def test_块内异常不被吞() -> None:
    with pytest.raises(ValueError, match="块里炸了"):
        with timed_span("会炸", timer=Ticker(0.0, 0.0), sink=lambda n, s: None):
            raise ValueError("块里炸了")


def test_sink为None时写日志(caplog: pytest.LogCaptureFixture) -> None:
    with caplog.at_level(logging.INFO, logger="w02.spans"):
        with TimedSpan("兜底", timer=Ticker(0.0, 1.25)):
            pass
    assert "兜底" in caplog.text
    assert "1.250s" in caplog.text


def test_出错时日志带标记(caplog: pytest.LogCaptureFixture) -> None:
    with caplog.at_level(logging.INFO, logger="w02.spans"):
        with pytest.raises(RuntimeError):
            with TimedSpan("兜底", timer=Ticker(0.0, 0.5)):
                raise RuntimeError("boom")
    assert "块内出错" in caplog.text
````

核心手法是 `Ticker` 类：它按剧本依次返回时间戳，**剧本用完就抛断言失败**。这样如果代码多调了一次 `timer()`，测试会立刻红，而不是悄悄多算一次。

```python
class Ticker:
    def __init__(self, *values):
        self._values = list(values)
        self.calls = 0

    def __call__(self):
        self.calls += 1
        if not self._values:
            raise AssertionError("timer 被调用的次数超出剧本")
        return self._values.pop(0)
```

有了它，耗时断言可以写等号而不是「大约」：

```python
ticker = Ticker(0.0, 3.0)
with TimedSpan("调模型", timer=ticker, sink=...) as span:
    pass
assert span.elapsed == 3.0          # 精确相等
```

### 9.4 一条实测出来的坑：别直接传 `iter([...])`

我第一版测试写的是 `collect(iter(pieces))`，其中 `pieces` 里混着一个 `TimeoutError`。结果红了：

```text
E   AttributeError: 'TimeoutError' object has no attribute 'choices'
```

原因：`iter(列表)` 就是普通的列表迭代器，**它不知道「列表里的异常实例要抛出去」**——那是我写在 `FakeStream.__iter__` 里的约定。所以它老老实实把 `TimeoutError` 当成一个 chunk 返回了，`iter_text` 去取 `.choices` 自然报错。

修正方式：**一律用 `FakeStream(...)`，不要用 `iter([...])`。**

这条值得记一下：**约定只在实现约定的那个类里有效。** 换成另一个「看起来一样能 for」的东西，约定就失效了。

### 11.1 本节学到的判断力

遇到一个新场景，问自己三个问题：

| 问题 | 是 → 用什么 |
|---|---|
| 这个结果是一次性给的，还是边算边给的？ | 边算边给 → 生成器 |
| 有没有「必须配对、且可能因异常漏掉」的两个动作？ | 有 → 上下文管理器 |
| 这个生成器会不会被提前丢弃？ | 会 → 必须用 `with` 管它，不能靠 GC |

### 11.3 和 03 的关系，一句话

**03 把「调用一个函数」这件事抽出去包住，04 把「一段执行过程」抽出去包住。** 前者只能看见函数的进出，后者能管住中间的每一步。所以流式这种「执行被推迟、过程可能中断」的场景，只能靠 04 的手段。
