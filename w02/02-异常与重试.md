**前置 1：`try / except / raise` 和自定义异常类**

```python
class MyError(Exception):        # 自定义异常 = 继承 Exception 的类，可以是空类
    pass

try:
    raise MyError("出事了")       # 主动抛出
except MyError as e:             # 主动接住
    print("接住了:", e)           # 接住了: 出事了
```

这一节要定义 `LLMError`、`RetryableError`、`FatalError` 三个异常类，就是把上面那个 `class` 写三遍，各加几个字段。

**前置 2：HTTP 状态码分五段，只有两段跟你有关**

```text
2xx 成功      200 OK
3xx 重定向    （API 调用里基本见不到）
4xx 你错了    400 参数不对 / 401 密钥无效 / 404 路径错 / 429 请求太快
5xx 我错了    500 / 502 / 503 / 504     服务端自己出故障
```

记住一句话：**4xx 是"你错了"，5xx 是"我错了"。** 别人错了可以再问一次；你自己错了再问一百次也是同一个答案。这一节所有的重试判断都建立在这句话上。

**前置 3：函数可以当参数传，也就能"延迟执行"**

```python
def run(fn):          # 参数是个函数
    return fn()       # 加括号才真正执行

run(lambda: 1 + 1)    # 2
```

`retry_call(lambda: client.chat.completions.create(...))` 用的就是这个：**把"要重试的那次调用"打包成一个函数传进去**，重试环负责反复调它，调用方不用关心重试逻辑。

## 2. 一次调用会以什么方式失败

先看清楚敌人。

你在 `pyproject.toml` 里装的 `openai` 包（SDK）替你做了三件事：拼 HTTP 请求、把返回的 JSON 变成对象、**把 HTTP 错误码翻译成 Python 异常**。所以调用失败时，你手上拿到的不是一个数字，而是一个异常对象。

要判断"该不该重试"，得先知道这些异常怎么分类。下面这张表在回答一个问题：**从每种异常对象上，能不能读到 HTTP 状态码？**

| 异常类 | 向上找父类的顺序 | 有 `status_code` 吗 |
| --- | --- | --- |
| `APITimeoutError` | → `APIConnectionError` → `APIError` → `OpenAIError` | **没有** |
| `APIConnectionError` | → `APIError` → `OpenAIError` | **没有** |
| `RateLimitError` | → `APIStatusError` → `APIError` → `OpenAIError` | 有（429） |
| `AuthenticationError` | → `APIStatusError` → `APIError` → `OpenAIError` | 有（401） |
| `InternalServerError` | → `APIStatusError` → `APIError` → `OpenAIError` | 有（5xx） |
| `BadRequestError` | → `APIStatusError` → `APIError` → `OpenAIError` | 有（400） |

第二列是 `openai.X.__mro__` 在本机实际打印出来的链（`__mro__` = Method Resolution Order，方法解析顺序，就是"向上找父类的顺序"；openai 3.37.0，只截到 `OpenAIError`，后面还有 `Exception` → `BaseException` → `object`）。它的用处只有一个：**决定你写几个 `except`**。写 `except APIError` 能一网打尽整张表；写 `except RateLimitError` 只抓 429。

第三列才是重点。**这张表藏着一个坑，也是很多人重试写错的根源：**

> 最常见的超时和连接中断，恰恰没有 `status_code`。

原因很简单：这两类失败**根本没有 HTTP 响应**——连接还没建立就断了，或者等到超时也没等到回音。没有响应，自然没有状态码。

所以「只看 `status_code` 决定要不要重试」的写法，会把**最该重试的那类错误漏掉**。我的 `classify()` 里因此有两道判断：先看 `status_code`，看不出来再按类型名兜底。

构造一个真实的 SDK 异常对象（不需要 API key，也不需要联网）：

```python
import httpx, openai

response = httpx.Response(429, request=httpx.Request("POST", "https://api.example.com"))
err = openai.RateLimitError(message="mock", response=response, body=None)

print(err.status_code)    # 429
print(str(err))           # mock
```

测试里就是这么造异常的 —— **能离线复现的故障才是好故障**。8.2 节把上面三行包成了一个函数 `_sdk_error(cls, status)`，测试里到处在调它。

### 为什么这件事值得认真做

一次调用单次失败率假设 10%（生产环境里网络抖动、限流、对端重启都算），**并且假设每次失败互相独立**，那么总共尝试 3 次仍然全失败的概率是：

```text
0.1 × 0.1 × 0.1 = 0.1³ = 0.001 → 0.1%
```

**从 10% 降到 0.1%，靠的只是加一个重试环。** 这也是为什么说它是整条链路上性价比最高的三十几行代码——`retry_call` 的全文（含函数头）一共 32 行，见第 7 节。

两个边界必须写清，否则这个数会被用错：

1. **"尝试 3 次"不等于"重试 3 次"。** 代码里的 `max_attempts=3` 指的是**总尝试次数**：首发 1 次 + 重试 2 次。所以 0.1³ 对应 3 次尝试；如果说成"重试 3 次"再算 0.1³，就是拿 3 次尝试的公式去描述 4 次尝试，对不上。同理，下面说的"多打两条日志"，就是多出来的那 2 次失败。
2. **独立性假设在真实世界经常不成立。** 对端整个挂掉时，3 次会一起失败，失败率还是 10% 而不是 0.1%。所以 0.1% 是**最好情况的上限**，只在失败源是随机抖动（丢包、偶发限流）时才成立。这一条同时解释了为什么"连续失败越多次，越该相信对方真的挂了"——见第 6 节的指数退避。

但如果分不清该不该重试，你会得到相反的效果：401 重试两轮，总耗时从 0.3 秒变成约 **2.1 秒**（本机实测：3 次尝试、每次 0.1 秒、默认退避 `0.5 + 1.0` 秒并带抖动，`attempts 3, elapsed 2.11s`），还多打了两条失败日志。

## 3. v1：在调用点写 try/except

这是绝大多数人第一版会写的东西（`client` 是 `openai.OpenAI()` 的实例，`time` 是标准库；这段是**示意**，本节不要求你跑它——真正能跑的是第 5 节之后我们自己的实现）：

```python
def summarize(text: str) -> str:
    for attempt in range(3):
        try:
            resp = client.chat.completions.create(
                model="gpt-4o-mini",
                messages=[{"role": "user", "content": text}],
            )
            return resp.choices[0].message.content
        except Exception:
            if attempt == 2:
                raise
            time.sleep(1)
```

### 3.1 逐行读：这 12 行到底在干什么

先不带评判地读一遍。下表按行号拆，它回答的问题是：**每一行删掉会怎样？**

| 行 | 代码 | 这一行在做什么 |
| --- | --- | --- |
| 1 | `def summarize(text: str) -> str:` | 定义函数：吃一段原文，吐一段摘要。`text: str` 和 `-> str` 是**类型注解**，不强制校验（传个 int 进去也不会当场报错），只给编辑器和读代码的人看 |
| 2 | `for attempt in range(3):` | `attempt` 依次取 **0、1、2**，一共 3 次机会。注意是"总共试 3 次"，不是"试 1 次再重试 3 次" |
| 3 | `try:` | 从这里到第 8 行是"可能会炸的那一段"。炸了不会退出函数，而是跳到第 9 行接着走 |
| 4 | `resp = client.chat.completions.create(` | 真正发请求的一行。三级点号各有用处：`client`（连的是哪家、用哪个 key）→ `.chat`（对话接口族）→ `.completions`（补全）→ `.create()`（把请求发出去）。返回值是一个 `ChatCompletion` 对象；**如果这行抛异常，`resp` 根本不会被赋值**，后面所有用到 `resp` 的代码都不会执行 |
| 5 | `model="gpt-4o-mini"` | 用哪个模型。写错会得到 404 `NotFoundError`（第 4 节表里那条） |
| 6 | `messages=[{"role": "user", "content": text}]` | 把 `text` 包成"一条用户消息"。**chat 接口吃的是消息数组，不是裸字符串**——因为模型要区分"谁说的话"。单轮对话就是长度 1 的数组。`role` 实测可取 `user` / `system` / `assistant`（新版 SDK 还有 `developer` / `tool` / `function`） |
| 7 | `)` | 参数收尾。注意第 6 行末尾那个逗号可以留，Python 允许尾逗号 |
| 8 | `return resp.choices[0].message.content` | 三次剥洋葱：`choices` 是候选回复列表（默认长度 1）→ `[0]` 取第一个 → `.message` 是那条回复的对象 → `.content` 才是**纯字符串**。少剥一层，拿到的是对象不是文本，拼字符串时会报 `TypeError` |
| 9 | `except Exception:` | 抓"几乎所有异常"。**抓不到 `KeyboardInterrupt` 和 `SystemExit`**（它们直接继承 `BaseException`，不是 `Exception` 的子类）——所以 Ctrl+C 仍然能正常打断，实测会落到 `except BaseException` 那一支 |
| 10 | `if attempt == 2:` | 只有第三次（下标 2）才进这个分支 |
| 11 | `raise` | **裸 `raise`**（不带异常名）：把"当前正在处理的这个异常"原样再抛一次。它不新建异常、不改原始 traceback——实测帧数 3；如果写成 `raise e`，会多一层"这里又抛了一次"，帧数变 4 |
| 12 | `time.sleep(1)` | 只有前两次失败会走到这里，睡 1 秒再进下一轮。第 3 次失败在第 11 行就抛出去了，**不会睡** |

光看代码还不够，得知道它跑起来什么行为。我用一个假 `client`（不发网络请求、只按剧本抛异常或返回结果）跑了这段代码，并把 `time.sleep` 换成记录器：

| 场景 | 调用次数 | 实际睡过 | 结果 |
| --- | --- | --- | --- |
| 三次全失败 | 3 | `[1, 1]` | 抛出 `TimeoutError`（**原始异常，没被包装**） |
| 第三次成功 | 3 | `[1, 1]` | 返回 `这是摘要` |

把 `sleep` 换回真的再跑一遍：**2.00 秒**。因为只有 2 次 `sleep(1)`，第 3 次直接抛。

最后一行代码 `return resp.choices[0].message.content` 里的 `resp` 长什么样？实测 `type(resp)` 是 `ChatCompletion`，`resp.choices[0].message.content` 是 `'这是摘要'`，`len(resp.choices)` 是 1。

读完这 12 行，你应该能看出它**没做**三件事：判断"这个错该不该重试"（`except Exception` 一视同仁）；把"试几次、等多久"抽出去（写死 `range(3)` 和 `sleep(1)`）；把失败信息翻译成人能读的语义（抛出来的还是裸 `TimeoutError`）。第 4 到 7 节就是分别补这三件事。

它确实能跑通。但下面四个问题都是真的：

| 问题        | 具体表现                                           |
| --------- | ---------------------------------------------- |
| **重试策略错** | `except Exception` 把 401、400 一起重试了 —— 这 2 秒是纯浪费  |
| **复制粘贴**  | 项目里 20 个调用点，每处都写一遍，改退避时间要改 20 处                |
| **测不了**   | 真要等 2 秒才能跑完这个测试（实测 2.00s）；你很快就会把这个测试注释掉                  |
| **信息丢失**  | 抛到上层的是裸 `TimeoutError`，`except Exception` 那一层拿不到"是限流还是密钥错"，只能给用户看 500 |

最要命的是第一条：**重试错了比不重试更糟**。不重试只是快失败，重试错了是"慢失败 + 三倍日志噪音"。

### 3.2 上面那两组数字怎么测的（可直接跑）

不用 API key、不联网，办法是造一个**假 client**：它的 `create()` 按剧本行动——剧本写 `"raise"` 就抛 `TimeoutError`，写 `"ok"` 就返回一个预先造好的 `ChatCompletion`。伪造返回值之所以可行，是因为 `ChatCompletion` 是个 Pydantic 模型，可以像 01 那样用 `model_validate` 从字典构造：

```python
import time
from openai.types.chat import ChatCompletion

RESP = ChatCompletion.model_validate({
    "id": "chatcmpl-1", "object": "chat.completion", "created": 0, "model": "gpt-4o-mini",
    "choices": [{"index": 0, "finish_reason": "stop",
                 "message": {"role": "assistant", "content": "这是摘要"}}],
})


class FakeCompletions:
    def __init__(self, plan):
        self.plan = list(plan)      # 剧本：["raise", "raise", "ok"]
        self.calls = 0

    def create(self, **kwargs):
        self.calls += 1
        action = self.plan.pop(0) if self.plan else "raise"
        if action == "raise":
            raise TimeoutError("fake timeout")
        return RESP


class FakeClient:
    def __init__(self, plan):
        self.chat = type("Chat", (), {})()
        self.chat.completions = FakeCompletions(plan)


def summarize(text, client):        # 与上面 12 行完全同体，只把 client 从全局变成参数
    for attempt in range(3):
        try:
            resp = client.chat.completions.create(
                model="gpt-4o-mini",
                messages=[{"role": "user", "content": text}],
            )
            return resp.choices[0].message.content
        except Exception:
            if attempt == 2:
                raise
            time.sleep(1)


slept = []
time.sleep = lambda s: slept.append(s)      # 只在本进程内把真的 sleep 换掉

c = FakeClient(["raise", "raise", "raise"])
try:
    summarize("原文", c)
except TimeoutError as e:
    print("A 调用次数:", c.chat.completions.calls, "| 睡过:", slept, "| 抛出:", type(e).__name__)

slept.clear()
c = FakeClient(["raise", "raise", "ok"])
print("B 返回:", summarize("原文", c), "| 调用次数:", c.chat.completions.calls, "| 睡过:", slept)
```

实测输出（本机）：

```text
A 调用次数: 3 | 睡过: [1, 1] | 抛出: TimeoutError
B 返回: 这是摘要 | 调用次数: 3 | 睡过: [1, 1]
```

三个要点：

- **假 client 必须长得像真的**：`client.chat.completions.create` 这一串属性一层都不能少，因为被测试的代码就是那么点下去的。这叫"鸭子类型"——只要叫声像鸭子（有同名属性/方法），函数就当它是鸭子。
- `time.sleep = lambda s: slept.append(s)` 是**改模块属性**，影响的是整个进程。跑完这个脚本进程就退出，不会污染别的测试；但如果你在 pytest 里这么写，必须用 fixture 收尾还原，否则会串到别的用例上。这就是为什么第 7 节宁可把 `sleep` 做成**参数**——参数是局部的，改全局是有副作用的。
- 把 `slept` 打印出来，等于顺手验证了"第 3 次失败不睡"这条行为。不打印的话，你只能看到"抛了异常"，看不出它到底睡了几次。

## 4. 分类：哪些错值得再试一次

这是这一节的核心判断，必须背下来：

| 情形        | 典型异常                                          | 该重试 | 理由                             |
| --------- | --------------------------------------------- | --- | ------------------------------ |
| 超时        | `APITimeoutError`、`TimeoutError`              | ✅   | 网络抖动，下一秒可能就通                   |
| 连接断       | `APIConnectionError`、`ConnectionResetError`   | ✅   | 同上                             |
| 429 限流    | `RateLimitError`                              | ✅   | 服务端明确说"等会儿再来"                  |
| 5xx       | `InternalServerError`（500/502/503/504）        | ✅   | 服务端临时故障                        |
| 401 / 403 | `AuthenticationError`、`PermissionDeniedError` | ❌   | 密钥错，重试一百次也一样                   |
| 400 / 422 | `BadRequestError`                             | ❌   | 参数、schema 不对，是**你的**代码问题       |
| 404       | `NotFoundError`                               | ❌   | 模型名写错                          |
| 其他未知      | 任何别的                                          | ❌   | **不赌**。未知通常是程序 bug，重试只是让它失败得更慢 |

「5xx 重试、4xx 不重试」这个边界是 HTTP 协议本身的设计意图：**4xx 是"你错了"，5xx 是"我错了"**。别人错了可以再问一次，你自己错了再问也是同一个答案。

而 429 是 4xx 里唯一的例外——它说的是"你没错，只是太快了"。

### 判据一句话

> **重试的前提是：同样的请求下一次可能得到不同的结果。**  
> 请求本身有问题时，结果不会变；服务端抽风时，结果会变。

## 5. v2：给自己一层异常

现在的目标：**业务代码永远不 import openai**。换供应商时只改一个文件。

先把文件头读完，后面每一段代码都依赖它（`errors.py` 第 1–20 行）：

```python
"""W2-02 · 异常体系与重试。

一句话：把 SDK 那十几种异常收敛成「能重试」和「不能重试」两类，
       再给能重试的那一类套一个带指数退避的重试环。

为什么需要这一层：
  1. 业务代码不该 import openai / anthropic / 任何 SDK 的异常类——换供应商就全崩；
  2. 「重试」不是无脑循环，401 重试三次只是浪费三次时间；
  3. 重试要能测试，所以 sleep 必须可注入。

运行演示：..\\.venv\\Scripts\\python.exe -m w02.errors
"""
from __future__ import annotations

import random
import time
from collections.abc import Callable
from typing import TypeVar

T = TypeVar("T")
```

- `from __future__ import annotations`：让所有注解延迟成字符串求值。这样 `def retry_call(...) -> T` 里写 `T`、`classify` 里写 `-> LLMError`，即使名字还没定义也不会报 `NameError`。
- `import random` 给抖动用，`import time` 给 `time.sleep` 当默认值用。
- `T = TypeVar("T")`：类型变量。`retry_call(fn: Callable[[], T]) -> T` 的意思是"传进来一个返回 `str` 的函数，我就返回 `str`"。运行时它什么都不做，纯粹给类型检查器（和读代码的人）看。

然后是本节的三个异常类（第 23–43 行）：

```python
class LLMError(Exception):
    """本项目所有 LLM 相关异常的基类。

    业务代码只 except 这一层，永远不 import 第三方 SDK 的异常类。
    """

    def __init__(self, message: str, *, status: int | None = None) -> None:
        super().__init__(message)
        self.message = message
        self.status = status

    def __str__(self) -> str:
        return self.message if self.status is None else f"[{self.status}] {self.message}"


class RetryableError(LLMError):
    """瞬时故障：等一会儿再试可能就成功（超时、连接断、429 限流、5xx）。"""


class FatalError(LLMError):
    """确定性故障：重试一百次也一样失败（401 密钥错、400 参数错、格式不符）。"""
```

只有三个类，但结构上完成了两件事：

1. **统一基类** → 上层可以写 `except LLMError`，一句话兜住所有情况；
2. **二分语义** → `RetryableError` / `FatalError` 是**给重试逻辑看的**，不是给人看的。

### 翻译函数：`classify`

```python
# 标准库层面的瞬时故障
_RETRYABLE_BUILTIN = (TimeoutError, ConnectionError)

# SDK 里不带 status_code 的连接层异常，只能按类型名兜底
_RETRYABLE_TYPE_NAMES = frozenset(
    {"APITimeoutError", "APIConnectionError", "APIConnectionTimeoutError"}
)


def classify(exc: BaseException) -> LLMError:
    """把任意异常翻译成 RetryableError 或 FatalError。

    判断顺序很重要，别乱调：
      1. 已经是我们自己的异常 → 原样返回；
      2. 标准库超时/连接 → 可重试；
      3. 429 → 可重试；5xx → 可重试；4xx（除 429）→ 不可重试；
      4. 没有 status_code 的 SDK 连接异常 → 按类型名判可重试；
      5. 其余未知异常 → 一律不可重试（fail fast，别赌）。
    """
    if isinstance(exc, LLMError):
        return exc

    if isinstance(exc, _RETRYABLE_BUILTIN):
        return RetryableError(f"连接层失败：{type(exc).__name__}: {exc}")

    status = getattr(exc, "status_code", None)
    if status is None:
        status = getattr(exc, "status", None)

    if status == 429:
        return RetryableError("被限流，稍后重试", status=429)
    if isinstance(status, int) and 500 <= status < 600:
        return RetryableError(f"服务端故障 {status}，稍后重试", status=status)
    if isinstance(status, int) and 400 <= status < 500:
        return FatalError(f"请求本身有问题 {status}，重试无意义", status=status)

    if type(exc).__name__ in _RETRYABLE_TYPE_NAMES:
        return RetryableError(f"连接层失败：{type(exc).__name__}")

    return FatalError(f"未知异常，按不可重试处理：{type(exc).__name__}: {exc}")
```

这是 `errors.py` 第 46–85 行，一字未改。下面这张表把它拆成 5 步，每一步对应第 4 节那张判断表的一行——它要回答的问题是：**为什么这里的顺序不能调换？**

| 步 | 代码在问什么 | 命中后返回 | 为什么必须在这个位置 |
| --- | --- | --- | --- |
| ① | `isinstance(exc, LLMError)` | 原样返回 | 已经在第 5 节第一段被翻译过的异常，再翻一次会变成"套娃"：`RetryableError("连接层失败：RetryableError...")` |
| ② | 是不是 `TimeoutError` / `ConnectionError` | `RetryableError` | 标准库异常没有 `status_code`，只能靠类型先捞。这两类**一定**是瞬时的 |
| ③ | `status == 429` / `5xx` / `4xx` | 可重试 / 可重试 / 不可重试 | 有状态码时，状态码最权威，所以放在类型名兜底之前 |
| ④ | 类型名在 `_RETRYABLE_TYPE_NAMES` 里 | `RetryableError` | 超时、连接断开这类 SDK 异常**没有** `status_code`，被 ③ 全漏掉，只能在这里靠 `type(exc).__name__` 兜 |
| ⑤ | 都不是 | `FatalError` | 未知 = 大概率程序 bug，重试只会让它失败得更慢，不如立刻暴露 |

三个容易看漏的实现细节：

**细节 1：为什么 `status` 要分两句写，不能写 `or`。**

```python
status = getattr(exc, "status_code", None) or getattr(exc, "status", None)
```

`or` 会把"属性不存在"和"属性存在但值是假值"混为一谈。本机实测：构造一个 `status_code = 0`、`status = 429` 的异常对象，`or` 写法拿到 `429`，分两句写拿到 `0`——`0` 会走到 ⑤ 变成 `FatalError`，而 `429` 会变成"可重试"。这类差异平时碰不到，但 `status_code=0` 不是不可能（某些自研网关就用 0 表示"没拿到状态码"），所以这里按"只有 `None` 才算没有"来写。

**细节 2：`frozenset` 里的第三个名字 `APIConnectionTimeoutError`，在当前 SDK 里其实不存在。**

实测 `hasattr(openai, "APIConnectionTimeoutError")` 返回 `False`（openai 3.37.0，超时只有 `APITimeoutError`）。留着它是为了兜住旧版本 SDK 的类型名——这是**防御性代码**，不是当下必需。知道这一点，你读别人代码时看到"多写的判断"就不会困惑。

**细节 3：⑤ 的报错文案里带了 `: {exc}`。** 少了它，日志里只剩"未知异常，按不可重试处理：WeirdError"，看不到 `WeirdError` 到底说了什么；原始消息恰恰是排查时最值钱的那一行。

### 为什么值得多这一层

| 没有这一层                                    | 有这一层                        |
| ---------------------------------------- | --------------------------- |
| 业务代码 `from openai import RateLimitError` | 业务代码只 `import LLMError`     |
| 换 Anthropic → 改 20 个文件的 `except`         | 换供应商 → 只改 `classify()` 一个函数 |
| 上层拿不到语义，只能返回 500                         | 上层能区分"限流"（提示重试）和"密钥错"（告警）   |

这就是**边界层**（boundary layer）的意思：第三方框架的异常只允许在边界出现一次，之后全部用你自己的语言。W4 写 FastAPI 时，这个设计会直接变成 `@app.exception_handler(LLMError)` —— 一个 handler 管全部。

## 6. 退避与抖动

### 为什么不能固定 1 秒

假设你的服务有 100 个并发请求，服务端在 12:00:00 抽风了一秒，100 个请求全部失败。如果都固定等 1 秒再重试：

```text
12:00:01.000  100 个请求同时涌回去  ← 重试风暴
```

服务端刚缓过来就被 100 个请求再次打满，于是再失败、再等 1 秒……这叫**惊群**（thundering herd），是你自己制造的 DDoS。

### 指数退避 + 抖动

```python
def backoff_delay(
    attempt: int,
    *,
    base_delay: float = 0.5,
    max_delay: float = 8.0,
    jitter: float = 0.5,
) -> float:
    """第 attempt 次失败后该等多久：指数增长 + 上下浮动。

    attempt=1 → 0.5s 上下浮动 50% → [0.25, 0.75]
    attempt=2 → 1.0s 上下浮动 50% → [0.5, 1.5]
    attempt=3 → 2.0s 上下浮动 50% → [1.0, 3.0]
    """
    raw = min(base_delay * (2 ** (attempt - 1)), max_delay)
    return raw * (1 + random.uniform(-jitter, jitter))
```

这是 `errors.py` 第 88–102 行。两行正文，拆开看：

- `2 ** (attempt - 1)`：`attempt` **从 1 开始数**（不是 0），所以第 1 次失败是 `2**0 = 1` 倍、第 2 次 2 倍、第 3 次 4 倍。这就是"指数"的全部含义。
- `min(..., max_delay)`：先封顶，防止 `2 ** 30` 算出一个天文数字。
- `random.uniform(-jitter, jitter)` 产出 `[-0.5, 0.5]` 之间的一个随机数，`1 + 它` 就是 `[0.5, 1.5]` 的乘数。**乘性**抖动，不是加减固定秒数。

代入 `base_delay=0.5, jitter=0.5` 算出来是这样：

| 第几次失败 `attempt` | `raw = min(0.5 × 2^(attempt-1), 8.0)` | 乘 `[1-0.5, 1+0.5]` 后实际范围 |
| ----- | ---- | ------------------------------- |
| 1     | 0.5s | 0.25 – 0.75s                    |
| 2     | 1.0s | 0.50 – 1.50s                    |
| 3     | 2.0s | 1.00 – 3.00s                    |
| 4     | 4.0s | 2.00 – 6.00s                    |
| 5     | 8.0s | 4.00 – 12.00s（已封顶，但抖动仍会把它顶过 8s） |
| 6 以上 | 8.0s | 同上                            |

两个设计点：

1. **指数**：第一次急（0.5s），越往后越有耐心（8s）。因为连续失败通常意味着对方真的挂了，急着重试没意义。
2. **抖动**（jitter）：`random.uniform(-jitter, jitter)` 让 100 个客户端在同一时刻算出的等待时间**各不相同**，重试就被摊平到 0.25–0.75 秒这个区间里，不再同时抵达。

**`max_delay` 不是最终值的硬上限**，它只封顶 `raw`。因为 `min()` 在前、乘抖动在后，封顶值仍然会被抖动放大到 `1.5 × max_delay`。本机实测 `backoff_delay(6, base_delay=0.5, max_delay=8.0, jitter=0.5)` 连抽 5 次得到 `6.41 / 8.11 / 7.19 / 5.00 / 4.38`——其中 8.11 已经超过 8.0。要真正硬顶住，得写成 `min(raw * (1 + ...), max_delay)`。这不是 bug，是取舍：封顶的意义是"别等一小时"，多等 4 秒无所谓。

> 别把抖动写成 `random.uniform(0, delay)` —— 那平均等待会变成一半，参数含义就乱了。用乘性抖动 `delay * (1 ± jitter)`，`delay` 才仍然是"期望等待时间"。

## 7. 重试环

### 7.1 全文

`errors.py` 第 105–136 行，全文如下（32 行，包括函数头、文档字符串和最后的兜底 `raise`）：

```python
def retry_call(
    fn: Callable[[], T],
    *,
    max_attempts: int = 3,
    base_delay: float = 0.5,
    max_delay: float = 8.0,
    jitter: float = 0.5,
    sleep: Callable[[float], None] = time.sleep,
    on_retry: Callable[[int, LLMError, float], None] | None = None,
) -> T:
    """执行 fn，遇到可重试错误就退避后重来，最多 max_attempts 次。

    抛出的一定是 LLMError 的子类（原始异常挂在 __cause__ 上）。
    """
    if max_attempts < 1:
        raise ValueError("max_attempts 至少为 1")

    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except BaseException as exc:  # 边界层就是要兜住一切，逐层翻译
            err = classify(exc)
            if not isinstance(err, RetryableError) or attempt >= max_attempts:
                raise err from exc
            delay = backoff_delay(
                attempt, base_delay=base_delay, max_delay=max_delay, jitter=jitter
            )
            if on_retry is not None:
                on_retry(attempt, err, delay)
            sleep(delay)

    raise AssertionError("循环一定会在里面 return 或 raise，走不到这里")
```

### 7.2 逐块说明

这张表在回答一个问题：**这 32 行里，每一行为什么必须存在？** 它也是全节最该读懂的一段。

| 代码 | 作用 |
| --- | --- |
| `fn: Callable[[], T]` | 接收一个**无参函数**。参数必须提前用 `lambda` 或 `functools.partial` 包好，`retry_call` 本身不接受业务参数——下一节 03 会把这个签名变成装饰器 |
| `*,` 后面全是 keyword-only | 强制调用方写 `max_attempts=3`，不能写 `retry_call(fn, 3)`。这类"人一多就传错位置"的参数一律这么做 |
| `if max_attempts < 1: raise ValueError` | 参数校验放在最前面。`max_attempts=0` 时 `range(1, 1)` 是空循环，函数会静默返回 `None`——比报错可怕得多 |
| `for attempt in range(1, max_attempts + 1)` | `attempt` 从 **1** 开始，和 `backoff_delay` 的入参口径一致 |
| `except BaseException as exc` | 边界层要兜住**一切**，包括 `KeyboardInterrupt`。因为这里只做"翻译 + 决定要不要重试"，翻完立刻按类别往外抛，不会吞掉中断 |
| `err = classify(exc)` | 唯一一次翻译。之后循环里只用 `err`，不再碰原始异常 |
| `if not isinstance(err, RetryableError) or attempt >= max_attempts` | 两个退出条件：不可重试，或次数用完。两者都要 `raise`，不能 `return None` |
| `raise err from exc` | 抛出去的是 `RetryableError`，但**原始异常挂在 `__cause__`** 上，traceback 里案发现场还在 |
| `if on_retry is not None:` | 回调：日志、埋点、报警都挂这里。判断 `is not None` 而不是 `if on_retry`，避免有人传进来一个假值对象 |
| `sleep(delay)` | 默认值是真睡，**测试时传假函数** —— 整个设计能被测试的原因 |
| 最后的 `raise AssertionError(...)` | 逻辑上走不到（循环内必定 `return` 或 `raise`），但静态检查器看不懂这一点，会以为函数可能返回 `None`。这行是写给类型检查器和未来改代码的人看的**护栏**：万一哪天有人改坏了缩进，它会立刻炸，而不是悄悄返回 `None` |

### 7.3 那段演示输出是怎么来的：`_demo()`

0.5 节看到的三段输出，来自 `errors.py` 第 139–182 行。它没有魔法，就是把 `sleep` 换成一个只打印的假函数：

```python
def _demo() -> None:
    def fake_sleep(seconds: float) -> None:
        print(f"      …… 实际会睡 {seconds:.2f}s（演示里不睡）")

    def log(attempt: int, err: LLMError, delay: float) -> None:
        print(f"      第 {attempt} 次失败：{err} → 退避 {delay:.2f}s")

    print("场景 1：前两次超时，第三次成功")
    state = {"n": 0}

    def flaky() -> str:
        state["n"] += 1
        if state["n"] < 3:
            raise TimeoutError("read timeout=30.0")
        return "第三次成功"

    print("   结果：", retry_call(flaky, sleep=fake_sleep, jitter=0, on_retry=log))
    print("   总调用次数：", state["n"])

    print("\n场景 2：401，不该重试")
    def unauthorized() -> str:
        raise FatalError("密钥无效", status=401)

    try:
        retry_call(unauthorized, sleep=fake_sleep, jitter=0, on_retry=log)
    except LLMError as e:
        print("   结果：直接失败 →", e)

    print("\n场景 3：三次都是 503，耗尽重试")
    state2 = {"n": 0}

    def always_503() -> str:
        state2["n"] += 1
        raise RetryableError("服务端故障 503，稍后重试", status=503)

    try:
        retry_call(always_503, sleep=fake_sleep, jitter=0, on_retry=log)
    except LLMError as e:
        print("   结果：", type(e).__name__, "→", e)
        print("   总调用次数：", state2["n"])


if __name__ == "__main__":
    _demo()
```

三个值得注意的写法：

- `state = {"n": 0}` 用字典存计数器，是因为闭包里改 `int` 要写 `nonlocal`，字典直接改字段更省事。
- 三个场景都传了 `jitter=0`。**不传的话每次输出的小数位都不一样**，你就没法判断"0.50 / 1.00"是算对了还是碰巧。
- `__name__ == "__main__"` 让 `python -m w02.errors` 能跑演示，而 `pytest` 导入这个模块时**不会**触发演示（否则测试输出里会混进三屏打印）。

### 7.4 `sleep` 注入：可测试性的关键

如果 `sleep` 写死在函数里，测「三次都失败」这个用例要真等 0.5 + 1 = 1.5 秒。一旦项目里有 20 个这样的测试，你会在半年后把它们全标成 `@pytest.mark.skip`。

注入之后，测试里传一个记录器就行。下面这段是可直接运行的完整代码（本机实测输出 `slept [0.5, 1.0, 2.0]`）：

```python
from w02.errors import RetryableError, retry_call

slept: list[float] = []

def always_timeout() -> str:
    raise TimeoutError("timeout")

try:
    retry_call(always_timeout, max_attempts=4, base_delay=0.5, jitter=0, sleep=slept.append)
except RetryableError as e:
    print("抛出的类型：", type(e).__name__)

print("睡过的时长：", slept)      # [0.5, 1.0, 2.0]
```

`max_attempts=4` → 尝试 4 次 → 中间睡 3 次 → 0.5 / 1.0 / 2.0。**零耗时，还顺便验证了退避曲线对不对。**

这个技巧不只用于重试：凡是涉及时间、随机、网络、文件的函数，都把那个东西做成参数传进来。如果 `sleep` 写死在函数里，测「三次都失败」这个用例要真等 0.5 + 1 = 1.5 秒；一旦项目里有 20 个这样的测试，你会在半年后把它们全标成 `@pytest.mark.skip`。

### 8.2 测试覆盖的 23 个用例，分三组

`test_errors.py` 一共 23 条，按用途分成三组：验证"分类对不对"的 12 条、验证"重试行为对不对"的 10 条、以及 1 条验收整个设计目标的。

**分类组（12 个 = 9 个参数化 + 3 个单测）**。参数化的那 9 条把第 4 节那张判断表逐行钉了一遍。

读代码前先把里面 4 个 pytest 记号认了，否则这段像天书。下表只回答一件事：**这几个记号各自是什么、不写它得费什么劲？**

| 记号 | 意思 | 不用它会怎样 |
| --- | --- | --- |
| `@pytest.mark.parametrize(("exc", "expected"), [...])` | "同一段测试跑多组数据"：列表里每一行拆成一次**独立**用例，函数参数 `exc`/`expected` 就接这一行的两列。9 行 = 9 条用例 | 手写 9 个几乎一样的函数，改一处漏 8 处 |
| `with pytest.raises(X):` | 断言"这段代码必须抛 X"，不抛就判红 | 自己写 `try/except` + `assert`，还容易写成"什么都没抛也算过" |
| `with pytest.raises(X) as info:` | 同上，并把异常对象留在 `info.value` 里，后面能查 `__cause__` 这类属性 | 拿不到异常对象，`test_原始异常挂在_cause_上` 根本没法写 |
| `pytest.fail("...")` | 主动判红，并打印这条消息 | 用 `assert False`，输出里只有一行 `AssertionError`，看不出你想说什么 |

```python
import httpx
import openai
import pytest

from w02.errors import FatalError, LLMError, RetryableError, backoff_delay, classify, retry_call


def _sdk_error(cls: type[Exception], status: int) -> Exception:
    """构造一个真实的 openai SDK 异常对象（不需要 API key）。"""
    response = httpx.Response(
        status, request=httpx.Request("POST", "https://api.example.com/v1/chat")
    )
    return cls(message="mock", response=response, body=None)


@pytest.mark.parametrize(
    ("exc", "expected"),
    [
        (TimeoutError("read timeout"), RetryableError),
        (ConnectionResetError("连接被重置"), RetryableError),
        (_sdk_error(openai.RateLimitError, 429), RetryableError),
        (_sdk_error(openai.InternalServerError, 500), RetryableError),
        (_sdk_error(openai.InternalServerError, 503), RetryableError),
        (openai.APITimeoutError(request=httpx.Request("POST", "https://x")), RetryableError),
        (_sdk_error(openai.AuthenticationError, 401), FatalError),
        (_sdk_error(openai.BadRequestError, 400), FatalError),
        (ValueError("完全陌生"), FatalError),
    ],
)

    assert isinstance(classify(exc), expected)
```

三个读法要点：

- **`_sdk_error` 就是第 2 节那三行代码**包成的函数。整个测试文件里所有"真 SDK 异常"都靠它造，一个 API key 都不用。
- 第 6 行（`APITimeoutError`）是全表最关键的一条：它没有 `status_code`，专门守着「漏判超时」这个坑。删掉 `classify()` 里按类型名兜底那个分支，这一条立刻变红。
- 500 和 503 各写一条，因为 `classify` 里的判断是区间 `500 <= status < 600`，两条是同一个分支的样本——**看着重复，其实是在验"区间判断"没有写死成 `== 503`**。

另外 3 条单测各管一件事：

```python

def test_分类保留状态码() -> None:

```

`is err` 不是 `== err`：这里验的是"同一个对象被原样递回来"，不是"内容相等"。用 `==` 的话，`classify` 就算重新 new 一个内容相同的异常也能过，套娃 bug 就测不出来。

## 10. 自测题

1. `APITimeoutError` 为什么不能用 `status_code` 判断？
2. `raise err from exc` 里的 `from exc` 有什么用？去掉会怎样？
3. 重试环里为什么必须要 `sleep` 这个参数？
4. 100 个客户端同时失败，不加抖动会发生什么？
5. 未知异常默认归为 `FatalError`，代价是什么？收益是什么？
6. 现在 `retry_call(retry_call(fn))` 这种套娃会发生什么？（提示：两次重试的乘积）

<details>
<summary>答案</summary>

1. 它继承自 `APIConnectionError`，是连接层失败，**根本没有 HTTP 响应**，所以没有 `status_code`。只能按类型名判。
2. 把原始异常记为 `__cause__`。去掉的话，traceback 只剩"服务端故障 503，稍后重试"，看不到底层是哪个请求、哪个 socket 出的问题，排查时失去上下文。
3. 为了可测试。真 `sleep` 会让测试耗时且不稳定；注入后可以在 0 毫秒内验证退避曲线。
4. 它们会在同一毫秒一起重试，形成**惊群**，把刚恢复的服务再次打满，可能引发连续失败。
5. 代价：某些本来可以重试的怪异常（比如某个新 SDK 的自定义类）不会被重试。收益：**不会因为重试一个程序 bug 而拖慢故障暴露**——bug 重试一百次还是 bug，但你多花了 100 倍时间才发现。
6. 外层 3 次 × 内层 3 次 = **最多 9 次调用**，退避时间也叠加。所以 `retry_call` 只在一个地方用（调用 SDK 的那一层），不要层层都包。
</details>

## 11. 一页速查

| 要做的事 | 写法 |
|---|---|
| 定义自己的异常 | `class X(LLMError)`，带 `status` |
| 判断该不该重试 | `classify(exc)` → `RetryableError` / `FatalError` |
| 重试一个调用 | `retry_call(lambda: client.chat.completions.create(...))` |
| 退避曲线 | `0.5 → 1 → 2 → 4 → 8`，乘性抖动 ±50% |
| 测试里不真等 | `sleep=list.append` |
| 保留原始现场 | `raise new from old` |
| 上层兜底 | 只写 `except LLMError` |

**下一节 03 装饰器**：现在 `retry_call(fn)` 需要把调用包成 lambda，读起来别扭。下一节把它变成 `@retry` 直接贴在函数上——那时你会真正理解装饰器为什么存在，而不是背语法。
